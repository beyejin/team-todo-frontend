## 자동 검사

### 2026-10-26 디자인 정리

Productivity의 회색·청록, Warm의 크림색·갈색 팔레트를 적용하고 Astryx CLI로 테마를 재생성했습니다. 장식 문구와 사이드바 하단 홍보 문구를 제거하고, 공유 작업 등록 영역·컬럼 제목·카드 이동 버튼을 간결하게 정리했습니다. API와 상태 처리 로직은 변경하지 않았습니다. 테마 라디오의 실제 이름에 맞춰 기존 테스트의 선택자를 갱신했습니다.

`npm run check`의 린트·포맷·타입·185개 테스트·빌드가 통과했습니다. 별도 코드 리뷰에서 기능·접근성 회귀는 발견하지 못했습니다. 브라우저 도구는 연결된 브라우저가 없고 `native pipe startup failed`를 반환해 실제 시각 검증은 하지 못했습니다. FE-KB-007의 두 테마·두 해상도 확인과 FE-007의 확장 없는 프로필 비교는 미실행 상태로 유지합니다. 실제 디자인 정리 업무 #14(`abe1587b-63fb-48af-845b-7a96d8cfdb0e`)를 공유 보드에 등록하고 CLI 상세 조회로 저장을 확인했으며, 시각 확인 전까지 진행 중으로 둡니다.

최신 `npm run check`에서 ESLint(경고 0), Prettier, strict TypeScript, Vitest **185개**, production build가 모두 통과했습니다. 건너뛴 프론트 테스트는 없습니다. 일반 Todo 서버 프록시를 포함한 모든 명세 경로가 빌드됐습니다. 최신 백엔드 검사는 **52개·CLI 51개** 통과입니다. 이 결과는 원격 DB 연결 검증과 구분합니다.

- API: 7개 동작, Task/TaskPage 런타임 검증, 400/401/404/422/500·비JSON·네트워크 오류, Abort 전달.
- 필터: 복수 상태, 기본값·URL 복원, 날짜 범위·잘못된 날짜, 변경하지 않은 날짜의 초·밀리초 보존.
- 폼: 제목 검증·전 필드 생성·PATCH 변경분·null/빈 배열 처리·응답 유실 안내·입력 보존·중복 제출 차단.
- 화면: 로딩/조회 실패/404 재시도, 최신 응답 유지, 삭제 취소·실패·중복 차단, 복구 후 마지막 페이지 보정.
- 탐색/테마: 링크·새로고침·뒤로/앞으로 보호, Next history 상태 보존, 쿠키 테마 복원·저장 제한 대응.

커밋 게이트는 실제 임시 Git/Husky에서 부분 스테이징 오류, 포맷 오류, 테스트 파일 삭제만 포함된 커밋을 차단하고 index·작업 내용을 보존하는 것까지 확인했습니다. 자세한 절차는 [HARNESS.md](HARNESS.md)에 기록했습니다.

## 과제 #8 칸반 추가 검증

2026-10-26 칸반 추가 당시 전체 검사에서 프론트 **148개**(기존 95 + 칸반 클라이언트·화면 48 + 서버 프록시 5)가 통과했습니다. ESLint·Prettier·strict TypeScript·production build도 통과했습니다. 당시 백엔드 작업 트리의 전체 검사는 **백엔드 46개·CLI 51개**가 통과했으며, 격리 PostgreSQL 변수를 설정해 건너뛴 DB 검사가 없습니다. 이후 일반 Todo 프록시·배포 준비 변경을 포함한 최신 수치는 위 자동 검사 절을 따릅니다.

- 칸반: UUID·필드 검증, 100개 이후 전체 페이지, 조회 중 목록 변경·중복 카드 감지, 등록·버튼·드래그 이벤트, 중복 요청 차단, 실패 시 입력·원위치 보존.
- 프록시: 토큰 서버 한정 사용, 허용 경로, 교차 사이트 쓰기 거부, no-store, 내부 오류 비노출. 서버 응답 유실이 JSON 502가 되는 경우도 재등록 전에 저장 여부 확인을 안내합니다.
- 백엔드: 같은 상태 요청의 불변성, 보드·멤버 범위, 목표 컬럼 누락, 트랜잭션 롤백, 동시 생성·이동 순서, 제한 역할의 최소 UPDATE 권한.

### 실제 Supabase — 연결과 업무 저장 확인

연결 전 Supabase 대시보드의 읽기 전용 조회로 `kanban-team6` 프로젝트, 기존 `Assignment #3 Board`, 세 상태 컬럼, 기존 업무 4개, workspace 멤버와 `ttodo_worker` 역할을 확인했습니다. 당시 없던 상태 이동용 UPDATE 권한은 아래 사용자 SQL 실행 후 다시 확인했습니다.

2026-10-26 사용자가 SQL Editor에서 서버 계정 비밀번호 재설정과 `002_worker_status_update.sql`에 해당하는 최소 권한을 적용했습니다. 새 DB 연결에서 `current_user=ttodo_worker`, `board_items.column_id`와 `issues.updated_at`의 UPDATE 권한이 모두 `true`임을 확인했습니다. 기존 보드 이름과 업무 4건도 일치했습니다. 비밀번호·검증 문자열·접속 URL은 기록하지 않습니다.

Production의 `KANBAN_DATABASE_URL` 비밀 환경변수를 반영하고 백엔드를 재배포했습니다. 무토큰 요청은 401, 유효 토큰의 칸반 목록 GET은 200·`total=4`였습니다. Vercel CLI로 인증한 프론트 production `/api/kanban/tasks` GET도 200·`total=4`여서 실제 서버 프록시 경유 조회를 확인했습니다.

실제 업무 `과제 #8 칸반 배포 및 데모 영상 제작`을 CLI로 등록할 때 요청이 5초 제한으로 종료됐습니다. 다시 등록하지 않고 백엔드 GET을 조회해 아래 저장 결과를 확인했습니다.

| 항목                 | 확인값                                 |
| -------------------- | -------------------------------------- |
| 업무 UUID            | `8bd6b2e8-02ef-4196-a7a2-dd268026b1e6` |
| 업무 번호            | `13`                                   |
| 등록 직후 GET 상태   | `assigned`                             |
| 등록 후 보드 전체 수 | `5`                                    |

백엔드를 서울 `icn1` 리전으로 재배포한 뒤 배포 API에서 `dpl_GhDnuo6P6t1ocqCb5JeGh8YNjRzi`의 READY·`regions=['icn1']`을 확인했습니다. 기존 칸반 목록 조회는 9.52초, 리전 변경 후 같은 목록 GET 200·`total=5`는 0.71초였습니다. 각각 한 번 측정한 값이며 평균 응답 시간이나 부하 성능 검증은 아닙니다. 이후 CLI의 같은 업무 상세 조회도 성공했습니다.

인증된 프론트 production `/api/kanban/tasks/8bd6b2e8-02ef-4196-a7a2-dd268026b1e6`에 HTTP PATCH로 `in_progress` → `completed` → `in_progress`를 요청했습니다. 세 응답 모두 200이며 요청 상태와 일치했습니다. 마지막 PATCH 응답의 `updated_at`은 `2026-10-26T10:41:50.676494Z`입니다. 영상 제작이 남아 있으므로 업무는 진행 중 상태로 둡니다. 이 확인은 브라우저 버튼·드래그 조작 검증이 아닙니다.

최종 프론트 목록 GET은 200·`total=5`였고 같은 UUID·업무 #13의 `in_progress`와 위 수정 시각이 유지됐습니다. Supabase의 새 연결에서 직접 SELECT한 결과도 해당 업무의 상태 범주가 `in_progress`로 일치했습니다. 기존 업무 #9(`in_progress`), #10(`todo`), #11(`done`), #12(`todo`)는 원래 상태를 유지했습니다.

일반 Todo는 `DATABASE_URL` 미설정으로 503이며 칸반 연결과 별도입니다.

현재 브라우저 조작 연결이 없어 연결 후 UI·두 브라우저 공유·실제 드래그·영상은 확인하지 못했습니다. 사용자 수동 테스트 전체와 VoiceOver 낭독도 남은 항목입니다. 브라우저 연결 후 FE-KB-001부터 순서대로 진행합니다.

## 확인 범위와 남은 사용자 수동 확인

- 수동 테스트 문서 전체를 통과 처리하지 않습니다. 위에 적힌 실제 실행 흐름과 단위·컴포넌트 검증을 구분합니다.
- VoiceOver 낭독, 모든 브라우저 조합, 브라우저 완전 종료 후 재방문, 두 테마×두 해상도 전체 CRUD 조합은 사용자 수동 확인 항목으로 남깁니다.
- Chrome에서 여러 요소에 `style="user-select:auto"`가 추가되는 React hydration 경고가 보고됐습니다. 2026-10-26 재확인에서 `src`에는 해당 스타일을 추가하거나 hydration 경고를 억제하는 코드가 없었고, 로컬 `/settings`·`/kanban`의 서버 HTML은 모두 200이며 해당 스타일을 포함하지 않았습니다. 서버 쿠키의 테마를 클라이언트 초기값으로 전달하는 코드도 확인했습니다. 광범위한 동일 스타일 삽입은 브라우저 확장의 HTML 변경을 강하게 시사하지만, 특정 확장과 실제 원인은 확정하지 않았습니다. [Next.js 공식 문서](https://nextjs.org/docs/messages/react-hydration-error)도 확장의 HTML 변경을 가능한 원인으로 설명합니다.
- 확장 없는 프로필의 초기 렌더링·두 테마 새로고침은 **미실행**입니다. [FE-007](TEST_CASE.md#fe-007--설정테마-지속저장-제한)의 비교 절차로 확인하며, 원래 프로필에서 경고가 났다는 사실을 자동 검사 통과로 대체하지 않습니다. 브라우저 조작 도구의 연결 실패와 앱 hydration 경고는 별도로 확인합니다.
- Playwright E2E 스위트는 추가하지 않았습니다. 실제 UI 확인은 브라우저를 직접 조작해 수행했습니다.
