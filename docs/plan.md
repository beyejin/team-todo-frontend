# 팀 Todo·공유 칸반 프론트엔드 명세 및 구현 계획

- 작성일: 2026-10-25 / 칸반 확장: 2026-10-26
- 상태: 프론트 구현 기준. 실제 실행 결과는 [VERIFICATION.md](VERIFICATION.md)에 별도로 기록합니다.
- 목적: 기존 Todo의 생성·조회·수정·삭제·복구를 유지하고, 팀 공유 칸반에서 실제 업무를 등록·조회·이동합니다.
- 문서 위치: 별도 `team-todo-frontend/docs/plan.md`. 초기 명세와 백엔드 계약 문서는 `team-todo-backend/docs`에서 가져왔습니다.

## 1. 요구사항과 적용 기준

사용자가 제공한 수업 자료 27·29쪽, 과제 #8 안내, 현재 백엔드 계약을 기준으로 합니다. 과제 #8은 과제 #7의 팀 공유 칸반 백엔드와 프론트엔드를 연결하고 실제 팀 업무를 저장·공유하는 것이 핵심입니다. Supabase라는 제품명 자체를 과제 #8의 별도 필수 조건으로 해석하지 않습니다. 이 프로젝트는 기존 팀 백엔드와 Supabase `kanban-team6` 저장소를 이어서 사용합니다.

| 항목      | 확정한 범위                                                                                |
| --------- | ------------------------------------------------------------------------------------------ |
| 기술      | Next.js, TypeScript, App Router                                                            |
| 필수 기능 | 할 일 생성·목록·상세·수정·소프트 삭제, 삭제 목록·복구, 필터·페이지 이동                    |
| 칸반 확장 | 별도 `/kanban`에서 팀 업무 생성·전체 조회, 세 상태 컬럼, 드래그와 버튼으로 상태 이동       |
| 테마      | Productivity와 Warm을 한 앱에서 전환                                                       |
| 첫 화면   | 저장된 테마를 적용한 할 일 목록. 테마 선택을 먼저 요구하지 않음                            |
| 설정      | 별도 `/settings` 화면에서 테마 선택                                                        |
| 연결      | 환경 변수로 지정한 로컬 백엔드, 기본 주소 `http://127.0.0.1:8000`                          |
| 제외      | 로그인·회원가입·관리자 화면, 실시간 알림, 영구 삭제, 칸반 내용 편집·삭제·컬럼 내 수동 정렬 |
| 완료 수준 | 표시만 되는 목업이 아니라 모든 포함 기능의 성공·실패 경로가 동작해야 함                    |

문서에서 정한 기본값은 Productivity 테마, 목록 20개, 완료 항목 포함입니다. 사용자에게 별도 인터뷰로 확정받은 값은 아니며, 이 계획의 구현 기본값으로 사용합니다.

칸반 인터뷰에서 확정한 사항은 **기존 Todo를 유지하고 팀 칸반 메뉴를 별도로 추가**, **드래그 이동과 명시적인 상태 변경 버튼을 함께 제공**하는 것입니다. 칸반은 새 업무를 `assigned`로 등록하고, 100개 단위 API 페이지를 끝까지 읽어 보드 전체를 표시합니다.

### 참고 예제와 현재 서버의 차이

수업 예제는 화면 구성의 참고 자료입니다. API는 현재 저장소의 [TSD](TSD.md), [데이터베이스 설계](database.md), 실제 라우터와 실행 중인 OpenAPI를 따릅니다.

| 항목           | 수업 예제                     | 현재 프로젝트에서 사용할 값            |
| -------------- | ----------------------------- | -------------------------------------- |
| API 경로       | `/api/v1/todos`               | `/api/v1/tasks`                        |
| 상태           | `TODO`, `IN_PROGRESS`, `DONE` | `assigned`, `in_progress`, `completed` |
| 우선순위       | 대문자 열거값                 | `low`, `medium`, `high`                |
| 담당자         | `assignee` 단일 값            | `assignees` 문자열 배열                |
| 마감일         | `due_date`                    | 시간대가 포함된 `due_at`               |
| 목록 기본 개수 | 50                            | 20                                     |
| 삭제           | `204`                         | `200`과 삭제된 Task 본문, 복구 가능    |

초기 수업 안내의 테마 선택 화면은 최신 요청에 따라 별도 설정 화면으로 구체화합니다. 예제 저장소에 표시된 구현·테스트 완료 내역은 이 프로젝트의 완료 내역으로 가져오지 않습니다.

## 2. 화면과 사용자 흐름

| 경로               | 화면         | 주요 동작                                                       |
| ------------------ | ------------ | --------------------------------------------------------------- |
| `/`                | 할 일 목록   | 필터, 페이지 이동, 생성 진입, 상세 진입                         |
| `/tasks/new`       | 할 일 생성   | 모든 입력 필드 편집, 저장·취소                                  |
| `/tasks/[id]`      | 할 일 상세   | 전체 필드 확인, 수정 진입, 삭제                                 |
| `/tasks/[id]/edit` | 할 일 수정   | 기존 값 표시, 변경 필드 저장, 취소                              |
| `/trash`           | 삭제된 할 일 | 삭제 목록, 복구, 페이지 이동                                    |
| `/kanban`          | 팀 칸반      | 팀 업무 등록·전체 조회, 상태별 컬럼, 드래그·버튼 이동, 새로고침 |
| `/settings`        | 설정         | 두 테마 선택, 현재 선택 표시                                    |

공통 탐색에는 할 일·팀 칸반·휴지통·설정을 둡니다. 모바일에서도 모든 화면과 생성 동작에 접근할 수 있어야 합니다.

### 목록과 필터

- 제목, 상태, 우선순위, 담당자, 마감일, 태그·라벨을 표시합니다. 완료 항목은 텍스트와 시각적 표시를 함께 사용합니다.
- 상태 복수 선택, 담당자, 우선순위, 마감일 범위, 태그, 라벨, 완료 포함 여부를 제공합니다.
- 상태 여러 값은 OR, 서로 다른 필터는 AND입니다. 담당자·태그·라벨은 정확히 일치하는 이름으로 조회하며 부분 검색으로 표시하지 않습니다.
- `status=completed`와 `include_completed=false`를 동시에 선택하면 결과가 없을 수 있음을 표시합니다. 서버 조건을 몰래 바꾸지 않습니다.
- 필터·페이지 상태는 URL 쿼리에 반영해 뒤로 가기와 새로고침에서 유지합니다. 필터가 바뀌면 `offset=0`으로 돌아갑니다.
- 목록은 서버의 생성 시각·ID 내림차순을 따릅니다. 서버에 없는 제목 검색이나 마감일 정렬을 지원한다고 표시하지 않습니다.
- 최초 빈 목록, 필터 결과 없음, 로딩, 조회 실패를 구분합니다. 조회 실패에는 재시도 동작을 제공합니다.

### 생성·상세·수정

- 생성·수정에서 제목, 설명, 상태, 우선순위, 마감일, 복수 담당자, 태그, 라벨을 편집할 수 있습니다.
- 제목은 공백만 입력할 수 없습니다. 제목·설명 등의 최대 길이를 기존 API 계약처럼 임의로 제한하지 않습니다.
- 담당자·태그·라벨은 자유 입력 문자열 목록입니다. 실제 계정 검색이나 자동 멤버 인증을 제공하지 않습니다.
- 상세 화면에는 생성·수정 시각도 표시합니다. 마감일이 없으면 `미지정`으로 표시합니다.
- 생성 성공 후 해당 상세 화면으로 이동합니다. 수정 성공 후 상세 화면에서 서버 응답을 확인합니다.
- 수정은 변경한 필드만 PATCH로 전송합니다. 취소하면 요청을 보내지 않고, 저장하지 않은 변경이 있는 상태에서 화면을 벗어나려 하면 확인합니다.
- 제출 중에는 해당 저장 동작을 막아 중복 요청을 방지합니다. 실패하면 입력값을 보존하고 필드 오류 또는 재시도 안내를 표시합니다.
- 실패한 생성 요청을 자동 재전송하지 않습니다. 응답 유실로 저장 여부가 불확실하면 목록 확인 후 사용자가 다시 시도하게 합니다.

### 삭제·휴지통·복구

- 삭제 전에 대상 제목과 휴지통 이동 안내를 보여주고 취소·삭제를 선택하게 합니다.
- 삭제 성공 후 활성 목록으로 이동하고 다시 조회합니다. 실패하면 성공 메시지를 표시하거나 항목을 숨기지 않습니다.
- 휴지통은 삭제 API가 보존한 Task 데이터를 표시합니다. 삭제된 항목의 일반 상세 GET은 404이므로 휴지통 내용을 보여주기 위해 호출하지 않습니다.
- 복구 성공 후 휴지통 목록을 갱신하고 활성 목록에서 항목을 확인할 수 있게 합니다. 기존 담당자·태그·라벨도 유지되어야 합니다.
- 삭제·복구로 현재 페이지가 비면 마지막 유효 페이지로 이동합니다. 영구 삭제 버튼은 제공하지 않습니다.

### 팀 칸반

- `/kanban`은 기존 Todo 목록과 다른 팀 공유 데이터입니다. 개인 Todo를 자동으로 칸반에 복사하지 않습니다.
- `assigned`는 **할 일**, `in_progress`는 **진행 중**, `completed`는 **완료** 컬럼에 표시합니다. 빈 컬럼도 이름과 개수를 표시합니다.
- 카드에는 업무 제목, 설명, 담당 GitHub 사용자명, 라벨과 상태를 표시합니다. API가 제공하는 작업 ID·번호로 같은 업무인지 확인할 수 있어야 합니다.
- 등록 폼은 제목 필수, 설명·담당자·라벨 선택입니다. 담당자와 라벨은 쉼표로 구분합니다. 담당자는 이미 팀에 등록된 GitHub 사용자명이어야 하며, 존재하지 않는 담당자로 실패하면 입력을 보존합니다.
- 등록 성공은 서버 응답 후 표시하며 새 업무를 할 일 컬럼에 반영합니다. 요청 중 등록을 막고, 실패·응답 유실 시 자동으로 중복 등록하지 않습니다.
- 카드마다 현재 상태 이외의 두 상태로 이동하는 버튼을 둡니다. 같은 동작을 데스크톱 드래그 앤 드롭으로도 실행할 수 있습니다. 모바일·키보드에서는 버튼으로 전체 상태 이동을 완료할 수 있어야 합니다.
- 상태 PATCH가 성공한 뒤 서버 응답으로 위치를 바꿉니다. 저장 중 중복 이동을 막고, 실패하면 원래 컬럼을 유지하며 오류와 재시도 방법을 표시합니다. 같은 컬럼에 놓으면 상태 변경을 요청하지 않습니다.
- 보드의 새로고침 동작으로 팀원이 바꾼 내용을 다시 읽습니다. 실시간 구독·자동 동기화를 제공한다고 표시하지 않습니다. 브라우저 새로고침과 별도 브라우저에서도 같은 저장 결과를 조회해야 합니다.
- 전체 페이지를 읽지 못한 경우 일부 카드만 있는 화면을 정상 전체 보드로 표시하지 않습니다. 기존 목록 유지 또는 오류 표시와 재시도를 제공합니다.
- 칸반 내용 수정·삭제는 현재 API 지원 범위 밖입니다. 동작하지 않는 버튼을 제공하지 않으며, 필요한 백엔드 계약은 [KANBAN_API_CHANGES.md](KANBAN_API_CHANGES.md)에 별도로 정리합니다.

## 3. 두 테마와 설정

- 설정 화면에서 Productivity·Warm의 이름과 미리보기를 보여주고 하나를 선택하게 합니다.
- 선택 즉시 공통 탐색, 목록, 폼, 상세, 휴지통, 칸반 컬럼·카드, 오류·확인 대화상자에 동일한 테마를 적용합니다.
- 테마 선택은 브라우저 쿠키 `team-todo-theme`에 저장해 경로 이동·새로고침·재방문 뒤에도 유지합니다. 유효한 값은 `productivity`, `warm`이며 없거나 잘못된 값이면 Productivity를 적용합니다.
- 서버가 첫 HTML을 만들 때 저장된 테마를 반영하고 클라이언트의 초기값도 맞춰 다른 테마가 잠깐 보이거나 hydration 오류가 나지 않게 합니다.
- 테마를 바꾸어도 할 일 데이터, 필터, 현재 페이지를 초기화하지 않습니다. 브라우저 저장이 제한되어도 현재 화면에서 선택·사용할 수 있어야 합니다.
- 컴포넌트를 테마별로 복제하지 않고 색상·글꼴·간격·모서리 등의 CSS 변수로 차이를 적용합니다.
- Productivity는 조밀하고 명확한 작업 화면, Warm은 따뜻한 표면과 여유 있는 간격이라는 두 가이드의 방향을 유지합니다. 한국어 글꼴 대체 목록을 포함합니다.
- 키보드 포커스, 입력 레이블, 오류 메시지 연결, 선택 상태를 제공합니다. 색상만으로 상태나 오류를 구분하지 않습니다.
- 375px 모바일과 1440px 데스크톱에서 주요 흐름을 검증하며, 모바일에서는 목록·폼을 한 열로 배치합니다.

두 원본 디자인 가이드를 이 폴더에 보존했습니다. 출처와 토큰 대응은 [DESIGN_MAPPING.md](DESIGN_MAPPING.md)에 기록했습니다.

두 가이드의 YAML 토큰과 본문 값이 충돌하는 부분은 YAML을 구현 기준으로 사용합니다. 공통 Astryx 컴포넌트에 두 테마를 적용하며 가이드 원문을 수정하지 않습니다.

## 4. API 계약과 데이터 처리

### 기존 Todo 연결 방식

- 프론트엔드 `.env.local`에 `NEXT_PUBLIC_API_BASE_URL=http://127.0.0.1:8000`을 설정합니다. `.env.example`에는 같은 로컬 예시를 제공합니다.
- 기존 Todo는 브라우저의 `fetch`가 백엔드에 직접 요청합니다. 칸반의 서버 프록시는 아래 별도 계약을 사용합니다.
- API 접근은 작은 공통 모듈로 모으고, URL 구성·JSON 처리·오류 변환만 공유합니다. 할 일 데이터는 서버를 기준으로 하며 브라우저 저장소로 대체하지 않습니다.
- 로컬 개발 서버에 `TTODO_API_TOKEN`이 없는 환경이 무인증 사용의 전제입니다. 토큰이 요구되면 연결 설정 오류로 알리며 로그인 화면을 만들거나 비밀 토큰을 프론트 공개 환경 변수에 넣지 않습니다.
- 개발 프론트 주소는 `http://localhost:3000`을 기본으로 합니다. 현재 작업 트리의 CORS 설정은 이 주소와 `http://127.0.0.1:3000`을 허용합니다. 다른 포트를 쓰면 서버의 `TTODO_CORS_ORIGINS`도 맞춰야 합니다.
- 기존 Todo의 무토큰 연결 조건은 팀 칸반 프록시의 서버 토큰 설정과 구분합니다. 기존 Todo의 인증 동작을 이 확장에서 바꾸지 않습니다.

### 요청과 응답

| 메서드 | 경로                         | 성공 응답                                     |
| ------ | ---------------------------- | --------------------------------------------- |
| GET    | `/api/v1/tasks`              | `200 TaskPage`                                |
| POST   | `/api/v1/tasks`              | `201 Task`                                    |
| GET    | `/api/v1/tasks/{id}`         | `200 Task`                                    |
| PATCH  | `/api/v1/tasks/{id}`         | `200 Task`                                    |
| DELETE | `/api/v1/tasks/{id}`         | `200 Task`, `deleted_at` 설정                 |
| GET    | `/api/v1/tasks/deleted`      | `200 TaskPage`                                |
| POST   | `/api/v1/tasks/{id}/restore` | `200 Task`, `deleted_at=null`, 요청 본문 없음 |

```ts
type Task = {
  id: number;
  title: string;
  description: string | null;
  status: "assigned" | "in_progress" | "completed";
  priority: "low" | "medium" | "high";
  due_at: string | null;
  assignees: string[];
  tags: string[];
  labels: string[];
  created_at: string;
  updated_at: string;
  deleted_at: string | null;
};

type TaskPage = {
  items: Task[];
  total: number;
  limit: number;
  offset: number;
};
```

이 타입은 실제 응답 생성 코드에서 확인한 계약입니다. OpenAPI의 응답 타입은 포괄적인 객체로 선언되어 있으므로 자동 생성 타입만으로 필드가 모두 확인된 것으로 보지 않습니다.

| 필드                          | 입력·표시 규칙                                                                              |
| ----------------------------- | ------------------------------------------------------------------------------------------- |
| `title`                       | 생성 시 필수. 앞뒤 공백 제거 후 빈 값 불가. 수정 시 `null` 불가                             |
| `description`                 | 선택 문자열. 비우기는 명시적 `null`                                                         |
| `status`                      | `assigned`=할당, `in_progress`=진행 중, `completed`=완료. 기본 할당, 상태 간 이동 제한 없음 |
| `priority`                    | `low`=낮음, `medium`=보통, `high`=높음. 기본 보통                                           |
| `due_at`                      | 선택 시각. 브라우저 현지 시각을 시간대가 있는 ISO 8601로 변환해 전송. 비우기는 `null`       |
| `assignees`, `tags`, `labels` | 문자열 배열. 공백·빈 항목·중복 정리, 초기값 `[]`                                            |
| 생성·수정·삭제 시각, `id`     | 서버가 결정하므로 편집 요청에 포함하지 않음                                                 |

날짜는 응답의 UTC 시각을 브라우저 시간대로 표시합니다. `datetime-local` 값을 시간대 없이 그대로 전송하지 않으며, 표시·재편집 시 같은 시각을 유지해야 합니다.

PATCH에서 생략한 필드는 유지합니다. 배열은 전달한 전체 값으로 교체하고 비울 때는 `[]`를 보냅니다. 현재 서버가 배열의 `null`을 받으면 변경을 건너뛰지만, 프론트는 변경 없음=생략·비우기=`[]`로 통일합니다. 제목·상태·우선순위는 OpenAPI의 nullable 표시와 달리 실제 검증에서 `null`이 거부되므로 전송하지 않습니다.

### 목록 쿼리

- `status`는 반복 쿼리로 전달합니다. 예: `status=assigned&status=in_progress`.
- `assignee`, `priority`, `tag`, `label`, `due_from`, `due_to`, `include_completed`, `limit`, `offset`을 지원합니다.
- 마감 범위는 양끝을 포함하며 시간대를 포함해야 합니다. 시작이 끝보다 늦으면 요청 전에 오류를 표시합니다. 범위 조회에서는 마감일이 없는 항목이 제외됩니다.
- `include_completed=true`, `limit=20`, `offset=0`이 기본입니다. `limit`은 1~100, `offset`은 0 이상입니다.
- 페이지 수와 이동 가능 여부는 현재 필터의 전체 개수인 `total`로 계산합니다. 필터 변경 중 이전 응답이 늦게 도착해 최신 결과를 덮지 않도록 처리합니다.
- 휴지통 목록은 `limit`, `offset`만 사용합니다. 활성 목록용 필터를 휴지통에서 지원한다고 표시하지 않습니다.

### 오류와 재조회

| 상황                      | 화면 동작                                                                         |
| ------------------------- | --------------------------------------------------------------------------------- |
| `400`                     | 잘못된 필터·날짜 범위를 안내하고 입력 수정 허용                                   |
| `422`                     | `detail` 검증 오류 배열을 해당 필드에 연결. 알 수 없는 항목은 폼 공통 오류로 표시 |
| `404`                     | 없거나 삭제된 항목 안내, 목록 복귀·재조회 제공                                    |
| `401`                     | 백엔드의 인증 설정 확인 안내. 로그인 흐름으로 전환하지 않음                       |
| `500`, `503`, 비JSON 응답 | 내부 응답을 그대로 노출하지 않고 일반 실패 안내·재시도 제공                       |
| 네트워크 연결 실패        | 서버 연결 오류를 표시하고 입력값 보존                                             |

TSD는 오류의 `detail` 필드를 설명하지만 예상 못한 서버 예외가 항상 JSON이라는 보장은 없습니다. HTTP 상태와 응답 형식을 함께 처리해야 합니다. 생성·수정·삭제·복구 성공 후에는 관련 목록·상세를 재조회해 새로고침 뒤에도 같은 데이터가 보이는지 확인합니다. 저장 실패를 성공처럼 보이게 하는 낙관적 갱신은 이 계획에서 사용하지 않습니다.

### 팀 칸반 연결과 API 계약

```text
브라우저 /kanban
  → 같은 출처의 Next.js /api/kanban/tasks
  → team-todo-backend /api/v1/kanban/tasks
  → 팀 Supabase kanban-team6의 기존 공유 보드
```

- Next.js 서버만 `TTODO_BASE_URL`과 `TTODO_API_TOKEN`을 읽고 필요한 인증 헤더를 붙입니다. 기본 백엔드 주소는 `http://127.0.0.1:8000`입니다. 브라우저는 같은 출처의 `/api/kanban/tasks`만 호출합니다. 토큰·DB 연결 문자열을 `NEXT_PUBLIC_` 환경 변수, HTML, 클라이언트 번들, 브라우저 저장소, 오류 응답에 넣지 않습니다.
- 백엔드가 `KANBAN_DATABASE_URL`, `KANBAN_BOARD_ID`, `KANBAN_ACTOR_PROFILE_ID`로 저장소·보드·작성자를 선택합니다. 프론트는 DB에 직접 연결하거나 임의의 보드 ID를 보내지 않습니다.
- 칸반 ID는 UUID 문자열입니다. 기존 Todo의 숫자 ID·우선순위·마감일·태그·삭제 필드 계약을 재사용하지 않습니다.
- 목록 응답은 `{ items, total, limit, offset }`입니다. `limit=100`으로 `total`까지 순차 조회하고, 응답의 필드·상태를 런타임에서 검사합니다.
- 등록 본문은 `{ title, description, status: "assigned", assignees, labels }`입니다. 상태 변경은 `{ status }`만 전달합니다.

| 동작      | 브라우저 경로                              | 백엔드 경로                         | 성공 기준                                |
| --------- | ------------------------------------------ | ----------------------------------- | ---------------------------------------- |
| 전체 조회 | `GET /api/kanban/tasks?limit=100&offset=…` | `GET /api/v1/kanban/tasks`          | `200`, 모든 페이지의 카드와 전체 수 일치 |
| 생성      | `POST /api/kanban/tasks`                   | `POST /api/v1/kanban/tasks`         | `201`, 공유 보드에 생성된 카드           |
| 상태 이동 | `PATCH /api/kanban/tasks/{UUID}`           | `PATCH /api/v1/kanban/tasks/{UUID}` | `200`, 서버가 반환한 새 상태·컬럼        |

상태 PATCH는 이 확장에서 추가하는 백엔드 변경입니다. 구현 범위와 향후 내용 편집·삭제 계약은 [백엔드 변경 문서](KANBAN_API_CHANGES.md)를 따릅니다. `401/403`은 인증·보드 멤버 설정, `404`는 사라진 카드, `409`는 대상 상태 컬럼, `422`는 입력, `503`은 연결 설정·일시적 사용 불가로 구분해 안내합니다. 실패를 빈 보드나 저장 성공으로 바꾸지 않습니다.

모의 응답을 이용한 실패 경로 테스트와 실제 API 확인을 구분합니다. 기존 Todo 통합 테스트는 별도 SQLite 파일을 사용합니다. 칸반의 실제 공유 확인은 팀이 수행할 실제 업무와 식별 가능한 제목을 사용하고 카드 ID를 기록합니다. 페이지 경계·오류 주입·대량 데이터 검증은 모의 응답이나 격리된 테스트 환경에서 수행합니다. 미실행·건너뛴 검사는 통과로 기록하지 않습니다.

## 7. 작성 시 확인과 남은 준비

- 2026-10-25에 로컬 `/openapi.json`이 HTTP 200으로 응답하며 위 7개 Todo 동작의 경로·메서드를 제공하는 것을 확인했습니다.
- API의 상세 필드와 오류 예외는 `app/main.py`, 요구사항은 [PRD](PRD.md)·[TSD](TSD.md)·[데이터베이스 설계](database.md)와 대조했습니다.
- 현재 문서는 프론트 구현 기준이며 배포 완료를 의미하지 않습니다. 기능별 검증은 별도 실행 기록을 따릅니다.
- 두 디자인 원본을 확보했고 YAML 우선 기준과 Astryx 토큰 대응을 기록했습니다.
