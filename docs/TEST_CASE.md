# Todo·팀 칸반 테스트 케이스

기존 Todo의 `TC-001~036`, 프론트의 `FE-001~013`, 팀 칸반의 `FE-KB-001~009`를 구분합니다. 현재 자동 검사와 직접 확인한 일부 흐름의 기록은 [VERIFICATION.md](VERIFICATION.md)를 봅니다. 이 문서의 체크 상태는 해당 수동 시나리오 전체를 확인한 뒤에만 갱신합니다.

## 공통 기준

- [ ] API 기본 경로는 `/api/v1`이며 JSON 필드명은 `snake_case`를 사용한다.
- [ ] 아래 요청은 별도 표시가 없으면 `Content-Type: application/json`을 사용한다.
- [ ] 성공 응답은 리소스 또는 목록을 반환한다. 목록 응답은 `items`, `total`, `limit`, `offset`을 포함한다.
- [ ] 할 일 상태와 우선순위는 API에서 각각 `assigned`, `in_progress`, `completed`와 `low`, `medium`, `high`를 사용한다. 사용자 표시명은 각각 `할당`, `진행 중`, `완료` 및 `낮음`, `보통`, `높음`이다.
- [ ] 오류 응답은 `detail`을 포함하며 내부 SQL이나 로컬 파일 경로를 노출하지 않는다.
- [ ] TSD에서 응답 필드 전체 형태와 일부 검증 오류 코드가 확정되지 않은 항목은 구현 계약에 맞춰 확인한다. 이 문서는 명시된 TSD 규칙(필터 오류 400, 리소스 없음 404, 본문 검증 실패 422)을 기준으로 한다.

## 할 일 생성

- [ ] **TC-001 필수 제목만으로 생성 성공**
  - 경로: `POST /api/v1/tasks`
  - 요청: `{"title":"기획서 작성"}`
  - 기대 응답: `201 Created`; 생성된 리소스에 `id`, `title`이 포함되고, 생략된 상태는 `assigned`, 우선순위는 `medium`으로 반환된다. 설명, 마감일, 담당자, 태그, 라벨은 비어 있다.

- [ ] **TC-002 선택 필드를 포함해 생성 성공**
  - 경로: `POST /api/v1/tasks`
  - 요청: `{"title":"API 구현","description":"Task CRUD","status":"in_progress","priority":"high","due_at":"2026-10-20T09:00:00+09:00","assignees":["민수","지윤"],"tags":["backend"," sprint "],"labels":["이번 주"]}`
  - 기대 응답: `201 Created`; 요청 값이 저장되어 반환된다. 날짜는 UTC ISO 8601로 정규화되고, 배열 문자열은 앞뒤 공백을 제거해 저장된다.

- [ ] **TC-003 담당자, 태그, 라벨 중복 및 공백 정리**
  - 경로: `POST /api/v1/tasks`
  - 요청: `{"title":"중복 정리","assignees":[" 민수 ","민수"],"tags":[" api ","api"],"labels":["중요"," 중요 "]}`
  - 기대 응답: `201 Created`; 각 목록에는 공백 제거 후 중복이 제거된 값이 한 번씩만 포함된다.

- [ ] **TC-004 제목 누락 또는 공백 제목 생성 실패**
  - 경로: `POST /api/v1/tasks`
  - 요청: `{"description":"제목 없음"}` 또는 `{"title":"   "}`
  - 기대 응답: `422 Unprocessable Entity`; `detail`에 입력 오류가 포함되고 할 일은 생성되지 않는다.

- [ ] **TC-005 허용되지 않는 상태 또는 우선순위 생성 실패**
  - 경로: `POST /api/v1/tasks`
  - 요청: `{"title":"잘못된 값","status":"blocked"}` 또는 `{"title":"잘못된 값","priority":"urgent"}`
  - 기대 응답: `422 Unprocessable Entity`; `detail`에 허용 값 오류가 포함되고 할 일은 생성되지 않는다.

- [ ] **TC-006 잘못된 날짜 형식 생성 실패**
  - 경로: `POST /api/v1/tasks`
  - 요청: `{"title":"날짜 오류","due_at":"다음 주"}`
  - 기대 응답: `422 Unprocessable Entity`; `detail`에 날짜 형식 오류가 포함되고 할 일은 생성되지 않는다.

## 목록 및 상세 조회

- [ ] **TC-007 기본 목록 조회 및 기본 페이지 값**
  - 경로: `GET /api/v1/tasks`
  - 요청: 쿼리 없음
  - 기대 응답: `200 OK`; 활성 할 일만 `items`에 반환되고 응답에 `total`, `limit`(기본 20), `offset`(기본 0)이 포함된다. 기본 정렬은 생성 시각 내림차순이다.

- [ ] **TC-008 상태 복수 필터 조회 성공**
  - 경로: `GET /api/v1/tasks?status=assigned&status=in_progress`
  - 요청: 위 쿼리
  - 기대 응답: `200 OK`; 지정한 상태 중 하나에 해당하는 활성 할 일만 반환된다.

- [ ] **TC-009 담당자, 우선순위, 태그, 라벨 복합 필터 조회 성공**
  - 경로: `GET /api/v1/tasks?assignee=%EB%AF%BC%EC%88%98&priority=high&tag=backend&label=%EC%9D%B4%EB%B2%88%20%EC%A3%BC`
  - 요청: 위 쿼리
  - 기대 응답: `200 OK`; 네 조건을 모두 만족하는 할 일만 반환된다. 결과가 없으면 빈 `items`와 `total: 0`을 반환한다.

- [ ] **TC-010 마감일 범위 필터 조회 성공**
  - 경로: `GET /api/v1/tasks?due_from=2026-10-01T00:00:00Z&due_to=2026-10-31T23:59:59Z`
  - 요청: 위 쿼리
  - 기대 응답: `200 OK`; 마감일이 범위 안에 있는 항목만 반환된다. 마감일이 없는 항목은 제외된다.

- [ ] **TC-011 완료 항목 포함 여부 필터 성공**
  - 경로: `GET /api/v1/tasks?include_completed=false`
  - 요청: 위 쿼리
  - 기대 응답: `200 OK`; `completed` 상태 항목은 제외된다. `include_completed`를 생략하면 완료 항목도 포함된다.

- [ ] **TC-012 페이지네이션 성공**
  - 경로: `GET /api/v1/tasks?limit=2&offset=1`
  - 요청: 위 쿼리
  - 기대 응답: `200 OK`; `limit: 2`, `offset: 1`을 반환하며 전체 정렬 결과에서 두 번째 항목부터 최대 2개를 `items`에 반환한다.

- [ ] **TC-013 유효하지 않은 목록 필터 실패**
  - 경로: `GET /api/v1/tasks?status=blocked` 또는 `GET /api/v1/tasks?priority=urgent`
  - 요청: 위 쿼리 중 하나
  - 기대 응답: `400 Bad Request`; `detail`에 잘못된 필터 값이 표시된다.

- [ ] **TC-014 페이지네이션 범위 초과 실패**
  - 경로: `GET /api/v1/tasks?limit=101`
  - 요청: 위 쿼리
  - 기대 응답: 요청이 거부된다(`limit` 최대 100). TSD에 따라 `422 Unprocessable Entity`와 검증 오류 `detail`을 반환한다.

- [ ] **TC-015 활성 할 일 상세 조회 성공**
  - 경로: `GET /api/v1/tasks/{task_id}`
  - 요청: `GET /api/v1/tasks/1`
  - 기대 응답: `200 OK`; ID가 1인 활성 할 일의 상세 리소스를 반환한다.

- [ ] **TC-016 존재하지 않는 할 일 상세 조회 실패**
  - 경로: `GET /api/v1/tasks/{task_id}`
  - 요청: `GET /api/v1/tasks/999999`
  - 기대 응답: `404 Not Found`; `detail`을 반환한다.

## 수정

- [ ] **TC-017 전달한 필드만 수정 성공**
  - 경로: `PATCH /api/v1/tasks/{task_id}`
  - 요청: `PATCH /api/v1/tasks/1` 본문 `{"title":"기획서 초안 작성"}`
  - 기대 응답: `200 OK`; 제목과 `updated_at`은 변경되고, 본문에서 생략한 나머지 값은 기존 값을 유지한다.

- [ ] **TC-018 배열 교체 및 빈 배열로 값 비우기 성공**
  - 경로: `PATCH /api/v1/tasks/{task_id}`
  - 요청: `PATCH /api/v1/tasks/1` 본문 `{"assignees":["지윤"],"tags":[]}`
  - 기대 응답: `200 OK`; 담당자 전체가 `지윤`으로 교체되고 태그 전체가 비워진다. 라벨 등 생략한 필드는 유지된다.

- [ ] **TC-019 null 허용 필드 초기화 성공**
  - 경로: `PATCH /api/v1/tasks/{task_id}`
  - 요청: `PATCH /api/v1/tasks/1` 본문 `{"description":null,"due_at":null}`
  - 기대 응답: `200 OK`; 설명과 마감일이 지워지고 그 외 필드는 유지된다.

- [ ] **TC-020 상태를 임의 순서로 변경 성공**
  - 경로: `PATCH /api/v1/tasks/{task_id}`
  - 요청: `PATCH /api/v1/tasks/1` 본문 `{"status":"completed"}`
  - 기대 응답: `200 OK`; 상태가 `completed`로 변경된다. 이후 `assigned` 등 다른 유효 상태로도 다시 변경할 수 있다.

- [ ] **TC-021 유효하지 않은 수정 값 실패**
  - 경로: `PATCH /api/v1/tasks/{task_id}`
  - 요청: `PATCH /api/v1/tasks/1` 본문 `{"status":"blocked"}`
  - 기대 응답: `422 Unprocessable Entity`; `detail`에 검증 오류가 포함되고 기존 리소스는 변경되지 않는다.

- [ ] **TC-022 존재하지 않는 할 일 수정 실패**
  - 경로: `PATCH /api/v1/tasks/{task_id}`
  - 요청: `PATCH /api/v1/tasks/999999` 본문 `{"title":"변경"}`
  - 기대 응답: `404 Not Found`; `detail`을 반환한다.

## 소프트 삭제와 복구

- [ ] **TC-023 할 일 소프트 삭제 성공**
  - 경로: `DELETE /api/v1/tasks/{task_id}`
  - 요청: `DELETE /api/v1/tasks/1`
  - 기대 응답: `200 OK`; 삭제 결과를 응답한다. 해당 항목은 기본 목록 및 상세 조회에서 더 이상 보이지 않는다.

- [ ] **TC-024 삭제된 할 일 목록 조회 성공**
  - 경로: `GET /api/v1/tasks/deleted`
  - 요청: 쿼리 없음
  - 기대 응답: `200 OK`; 삭제된 항목만 목록으로 반환하며 목록 메타데이터(`items`, `total`, `limit`, `offset`)를 포함한다.

- [ ] **TC-025 삭제된 할 일 상세 조회 실패**
  - 경로: `GET /api/v1/tasks/{task_id}`
  - 요청: 삭제된 ID로 `GET /api/v1/tasks/1`
  - 기대 응답: `404 Not Found`; 삭제된 항목은 일반 상세 조회에서 접근할 수 없다.

- [ ] **TC-026 삭제된 할 일 수정 실패**
  - 경로: `PATCH /api/v1/tasks/{task_id}`
  - 요청: 삭제된 ID로 `PATCH /api/v1/tasks/1` 본문 `{"title":"수정 시도"}`
  - 기대 응답: `404 Not Found`; 삭제된 항목은 수정되지 않는다.

- [ ] **TC-027 삭제된 할 일 복구 성공**
  - 경로: `POST /api/v1/tasks/{task_id}/restore`
  - 요청: `POST /api/v1/tasks/1/restore`
  - 기대 응답: `200 OK`; 복구된 리소스를 반환하고 `deleted_at`이 비워진다. 항목이 기본 목록과 상세 조회에 다시 나타난다.

- [ ] **TC-028 이미 삭제된 할 일 재삭제 실패**
  - 경로: `DELETE /api/v1/tasks/{task_id}`
  - 요청: 이미 삭제된 ID로 `DELETE /api/v1/tasks/1`
  - 기대 응답: `404 Not Found`; 삭제 상태가 중복 변경되지 않는다.

- [ ] **TC-029 활성 할 일 복구 시도 실패**
  - 경로: `POST /api/v1/tasks/{task_id}/restore`
  - 요청: 삭제되지 않은 ID로 `POST /api/v1/tasks/1/restore`
  - 기대 응답: `404 Not Found`; 활성 항목의 상태는 변경되지 않는다.

- [ ] **TC-030 존재하지 않는 할 일 삭제 및 복구 실패**
  - 경로: `DELETE /api/v1/tasks/{task_id}` 또는 `POST /api/v1/tasks/{task_id}/restore`
  - 요청: `task_id=999999`
  - 기대 응답: `404 Not Found`; `detail`을 반환한다.

- [ ] **TC-031 신규 DB 동시 첫 연결에서 마이그레이션 1회 적용**
  - 상황: 스키마가 없는 SQLite 파일에 여러 연결이 동시에 처음 접근한다.
  - 기대 결과: 모든 연결이 성공하고 테이블 및 마이그레이션 기록이 중복 생성되지 않는다.

- [ ] **TC-032 PostgreSQL에 저장한 할 일 생성 후 조회 성공**
  - 경로: `POST /api/v1/tasks`, `GET /api/v1/tasks/{task_id}`
  - 상황: `DATABASE_URL`로 지정한 PostgreSQL 테스트 DB에서 생성 API를 호출한 뒤 별도 조회 요청을 보낸다.
  - 기대 결과: 생성 응답은 `201`, 조회 응답은 `200`이며 제목, 담당자, 태그가 유지된다. SQLite fallback이 아니라 PostgreSQL에 저장되어야 한다.

- [ ] **TC-033 설정된 팀 API 토큰으로 보호**
  - 경로: `/api/v1/tasks`
  - 준비: 서버에 `TTODO_API_TOKEN`을 설정한다.
  - 기대 결과: 토큰이 없거나 다르면 `401`을 반환하고, `Authorization: Bearer <token>`이 맞으면 목록을 조회할 수 있다.

- [ ] **TC-034 기존 칸반 보드에 저장하고 다시 조회**
  - 경로: `POST /api/v1/kanban/tasks`, `GET /api/v1/kanban/tasks/{task_id}`, `GET /api/v1/kanban/tasks`
  - 준비: 별도 로컬 PostgreSQL에 기존 보드 테이블과 멤버, 프로젝트, 보드, 칼럼을 만들고 연결한다.
  - 기대 결과: 작업, 보드 배치, 멤버, 라벨을 저장한다. 새 요청의 상세 조회와 보드 목록에 같은 작업이 나타난다. SQLite나 별도 `tasks` 테이블에 저장하지 않는다.

- [ ] **TC-035 Worker 토큰 바인딩을 fail-closed로 검사**
  - 상황: Worker ASGI scope에 토큰 바인딩이 없거나 요청 토큰이 다르다.
  - 기대 결과: 토큰 바인딩이 없으면 `503`, 잘못된 토큰이면 `401`을 반환한다. Worker 외부 프로세스 환경변수에만 설정한 토큰을 바인딩으로 간주하지 않는다.

- [ ] **TC-036 Worker DB 설정 누락 시 SQLite fallback 차단**
  - 상황: Worker scope에 올바른 API 토큰은 있지만 PostgreSQL 연결 바인딩이 없다.
  - 기대 결과: `503`을 반환하고 SQLite 파일이나 로컬 마이그레이션을 만들지 않는다.

## 프론트엔드 수동 테스트 시나리오

기준은 [프론트엔드 명세](plan.md)의 FE-001~013입니다. 위 TC-001~036은 기존 백엔드 기준이며, 아래 수동 시나리오는 별도 실행 기록입니다. 구현 여부, 자동 검사, 수동 시나리오 전체 통과를 구분합니다. 문서 작성이나 백엔드 검사 통과를 화면 테스트 통과로 기록하지 않습니다. Playwright 기반 E2E는 추가하지 않습니다. 칸반은 문서 하단의 별도 준비와 FE-KB 시나리오를 사용합니다.

### 공통 준비와 기록 방법

1. [README](../README.md)에 따라 프론트를 실행합니다. 구현되지 않은 기능은 `미실행 — 구현 대기`, 실행 환경이 준비되지 않은 경우는 `막힘 — 사유`로 남깁니다. 아래 환경은 기존 Todo 전용이며 팀 칸반의 실제 공유 연결 확인을 대신하지 않습니다.
2. 백엔드 저장소에서 아래 명령으로 **기존 8000 서버와 분리된 테스트 서버**를 시작합니다. 기존 DB나 공유 보드를 사용하지 않습니다. 터미널은 종료할 때까지 열어 두고 테스트 DB 경로를 결과에 기록합니다.

   ```sh
   task_test_dir=$(mktemp -d "${TMPDIR:-/tmp}/team-todo-manual.XXXXXX")
   env -u DATABASE_URL -u KANBAN_DATABASE_URL -u TTODO_API_TOKEN \
     TODO_DB_PATH="$task_test_dir/todo.db" \
     uv run uvicorn app.main:app --host 127.0.0.1 --port 8001
   ```

3. 테스트용 프론트의 `.env.local`을 `NEXT_PUBLIC_API_BASE_URL=http://127.0.0.1:8001`로 설정하고 README의 개발 명령으로 시작합니다. 환경 변수 변경 후에는 프론트 서버를 재시작합니다. 브라우저는 `http://localhost:3000`을 사용합니다. 다른 포트라면 CORS 허용 출처도 맞춥니다.
4. 브라우저 개발자 도구의 Network에서 API 요청이 **8001**로 향하는지 확인합니다. `/openapi.json`은 200, 처음의 `GET /api/v1/tasks`는 `items: []`, `total: 0`이어야 합니다. 이 조건을 만족하기 전에는 샘플을 생성하지 않습니다.
5. 실행일시, 프론트·백엔드 버전, 브라우저 버전, 시간대, 뷰포트의 CSS 픽셀 크기, 테마를 기록합니다. 날짜 검증의 기준 시간대는 `Asia/Seoul`입니다. 다른 시간대를 쓰면 기대 현지 시각을 환산해서 기록합니다.
6. 각 시나리오의 준비 상태를 다시 맞춘 뒤 실행합니다. 이전 시나리오가 바꾼 항목을 그대로 사용해 기대 개수가 달라지지 않게 합니다. 데이터는 테스트 DB에서만 UI 또는 Swagger UI로 준비하며, 실제 CRUD 시나리오의 본 동작은 프론트 화면에서 수행합니다.
7. 결과는 `미실행/통과/실패/막힘` 중 하나로 기록합니다. 실패 시 단계 번호, 기대값·실제값, 관련 요청의 메서드·경로·상태, 스크린샷 또는 콘솔 오류를 남깁니다. 토큰·개인 데이터는 증거에 포함하지 않습니다.
8. 종료 후 브라우저의 네트워크 제한·응답 대체·쿠키 차단을 해제하고 테스트 서버를 `Ctrl+C`로 종료합니다. 테스트 DB는 결과 확인을 위해 보존합니다. 테스트용으로 바꾼 프론트 환경 변수는 원래 개발 설정으로 돌립니다.

### FE-001 — 첫 화면·빈 목록·로딩·연결 실패

**준비:** 빈 테스트 DB, 해당 사이트의 `team-todo-theme` 쿠키 없음. Network 기록을 켭니다.

| 단계 | 수행                                                                                 | 기대 결과                                                                                                        |
| ---- | ------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------- |
| 1    | `/`에 처음 접속합니다.                                                               | 테마 선택 단계 없이 Productivity 목록이 보입니다. 빈 목록 안내와 생성 진입 동작이 있고 오류로 표시하지 않습니다. |
| 2    | Network 속도를 Slow 3G로 바꾸고 새로고침합니다.                                      | 응답 전 로딩을 표시하며 이 구간을 빈 목록이나 조회 실패로 표시하지 않습니다. 응답 후 빈 목록으로 바뀝니다.       |
| 3    | Offline으로 바꾼 상태에서 앱의 목록 재조회 또는 화면 이동으로 API 조회를 일으킵니다. | 서버 연결 실패 안내와 재시도 동작이 보입니다. 데이터가 없다는 안내로 대체하지 않습니다.                          |
| 4    | Online으로 돌리고 재시도합니다.                                                      | 새 API 요청이 성공하고 빈 목록으로 회복합니다. 페이지 전체를 다시 설치하거나 초기화할 필요가 없습니다.           |

### FE-002 — 생성·검증·저장 유지

**준비:** 네트워크 제한을 해제합니다. 이번 실행의 고유 접두어(예: `수동-20261025-01`)를 제목에 사용합니다.

| 단계 | 수행                                                                                                                                                                                               | 기대 결과                                                                                                                                                              |
| ---- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1    | 제목 없이 저장하고, 공백만 넣어 다시 저장합니다.                                                                                                                                                   | 제목 입력 오류가 보이며 생성되지 않습니다. 다른 입력값은 보존됩니다.                                                                                                   |
| 2    | 제목만 `접두어-최소`로 입력해 저장합니다.                                                                                                                                                          | POST 201 한 건 뒤 새 상세로 이동합니다. 상태 `할당`, 우선순위 `보통`, 배열 `[]`, 설명·마감일 `null`이며 마감일은 `미지정`으로 표시됩니다.                              |
| 3    | 목록으로 이동하고 새로고침한 뒤 해당 상세를 다시 엽니다.                                                                                                                                           | 같은 ID와 값이 조회됩니다. 생성·수정 시각이 표시됩니다.                                                                                                                |
| 4    | 별도 항목에 제목 `접두어-전체`, 설명 `첫 설명`, 상태 `진행 중`, 우선순위 `높음`, 마감일 `2026-11-02 09:00`, 담당자 `민수`·`민수`·`지윤`, 태그 `api`·`api`, 라벨 `중요`·`중요`를 입력해 저장합니다. | 모든 선택 필드가 저장됩니다. 담당자는 `민수`·`지윤`, 태그는 `api`, 라벨은 `중요`로 공백·중복이 정리됩니다. 저장 요청의 마감일에는 시간대가 있습니다.                   |
| 5    | 날짜 입력을 불완전하게 만들거나 유효하지 않은 날짜 입력을 시도합니다.                                                                                                                              | 입력기가 차단하거나 필드 오류를 표시하며 잘못된 날짜로 생성하지 않습니다. 일반 UI로 만들 수 없는 잘못된 상태·날짜의 서버 검증은 FE-009의 422 응답으로 별도 확인합니다. |

### FE-003 — 부분 수정·값 비우기·상태 변경

**준비:** FE-002의 전체 필드 항목을 원래 값으로 맞춥니다. Network에서 PATCH 본문과 응답을 확인합니다.

| 단계 | 수행                                                                       | 기대 결과                                                                                                                          |
| ---- | -------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| 1    | 제목만 `접두어-전체-수정`으로 바꿔 저장합니다.                             | 변경한 제목만 PATCH에 전달합니다. ID·생성 시각·나머지 값은 유지하고 수정 시각을 갱신합니다. 상세와 새로고침 후 값이 같습니다.      |
| 2    | 설명과 마감일을 비우고 태그를 모두 제거한 뒤 저장합니다.                   | 요청은 `description: null`, `due_at: null`, `tags: []`를 포함합니다. 담당자·라벨은 유지되고 지운 값은 다시 조회해도 비어 있습니다. |
| 3    | 담당자를 `지윤` 한 명으로, 라벨을 빈 배열로 바꿉니다.                      | 배열 전체를 교체합니다. 남기지 않은 담당자와 라벨이 사라집니다. 배열을 `null`로 보내지 않습니다.                                   |
| 4    | `할당 → 완료 → 진행 중 → 할당` 순서로 저장하고 매번 상세를 새로고침합니다. | 단계 순서 제한 없이 상태가 저장됩니다. 화면 한 곳만 바뀌고 서버 값이 그대로인 상태는 실패입니다.                                   |
| 5    | 제목·상태·우선순위를 선택하지 않은 값으로 만들 수 있는지 확인합니다.       | 필수 값의 `null` 저장을 허용하지 않습니다. UI가 유효한 값만 선택하게 하면 그 동작을 기록합니다.                                    |

### FE-004 — 필터·페이지·URL·뒤로 가기

**준비:** 아래 네 항목을 생성합니다. `수동필터` 태그가 붙은 이전 항목이 있으면 다른 고유 태그를 정해 네 항목과 조회에 동일하게 사용합니다. 시간은 서울 기준입니다.

| 제목   | 상태    | 우선순위 | 마감일           | 담당자     | 태그               | 라벨 |
| ------ | ------- | -------- | ---------------- | ---------- | ------------------ | ---- |
| 수동-A | 할당    | 낮음     | 2026-11-02 09:00 | 민수       | 수동필터, frontend | 검증 |
| 수동-B | 진행 중 | 높음     | 2026-11-02 18:00 | 민수, 지윤 | 수동필터, backend  | 검증 |
| 수동-C | 완료    | 보통     | 2026-11-03 09:00 | 지윤       | 수동필터, frontend | 검증 |
| 수동-D | 할당    | 보통     | 미지정           | 없음       | 수동필터           | 없음 |

| 단계 | 수행                                                                                                                 | 기대 결과                                                                                                            |
| ---- | -------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| 1    | 태그 `수동필터`만 적용합니다.                                                                                        | 전체 개수 4, A~D가 생성 시각·ID 내림차순으로 표시됩니다.                                                             |
| 2    | 상태 `할당`과 `진행 중`을 함께 선택합니다.                                                                           | A·B·D만 표시되고 요청에 `status=assigned&status=in_progress`가 있습니다.                                             |
| 3    | 상태를 초기화하고 담당자 `민수`, 우선순위 `높음`, 라벨 `검증`을 적용합니다.                                          | 모든 조건에 맞는 B만 표시됩니다. 담당자를 `민`으로 바꾸면 0건이며 부분 일치 검색으로 동작하지 않습니다.              |
| 4    | 태그 외 조건을 초기화하고 마감 범위를 `11월 2일 09:00~18:00`으로 설정합니다.                                         | 양끝을 포함해 A·B만 표시됩니다. 마감일 없는 D는 제외됩니다. 시작을 끝보다 늦게 입력하면 요청 전 오류가 보입니다.     |
| 5    | 마감 범위를 비우고 완료 포함을 끕니다. 이어서 상태 `완료`만 선택합니다.                                              | 처음에는 A·B·D, 두 번째는 0건입니다. 완료 제외 조건을 자동으로 켜거나 상태 조건을 몰래 지우지 않습니다.              |
| 6    | 존재하지 않는 태그를 적용한 뒤 필터를 초기화합니다.                                                                  | 필터 결과 없음과 최초 빈 목록을 구분하고, 초기화 후 저장된 목록이 다시 보입니다.                                     |
| 7    | 별도 고유 태그 `수동페이지`를 붙인 항목 `P01`~`P21`을 UI 또는 Swagger로 순서대로 준비합니다. 해당 태그만 적용합니다. | `total=21`, 기본 `limit=20`. 첫 페이지 P21~P02, 다음 페이지 P01이며 중복·누락이 없습니다.                            |
| 8    | 다음 페이지에서 새로고침하고, 상세에 들어갔다가 브라우저 뒤로 가기를 누릅니다.                                       | URL과 화면의 태그·offset이 유지됩니다. 되돌아온 목록도 P01이며 임의로 첫 페이지가 되지 않습니다.                     |
| 9    | 다음 페이지에서 상태 필터를 변경합니다.                                                                              | offset이 0으로 초기화됩니다. 필터를 다시 바꾸고 뒤로/앞으로 가기를 실행하면 URL에 대응하는 필터·페이지가 표시됩니다. |

### FE-005 — 삭제 취소·삭제·휴지통

**준비:** 설명·담당자·태그·라벨이 있는 활성 항목의 ID와 값을 기록합니다.

| 단계 | 수행                                                                                                     | 기대 결과                                                                                                                              |
| ---- | -------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| 1    | 상세에서 삭제를 누르고 확인창의 제목·휴지통 안내를 읽은 뒤 취소합니다.                                   | 삭제 요청을 보내지 않으며 활성 목록·상세·서버 데이터가 유지됩니다.                                                                     |
| 2    | 삭제를 다시 눌러 확정합니다.                                                                             | DELETE 200과 `deleted_at`이 있는 Task 응답 뒤 활성 목록으로 이동합니다. 삭제된 항목이 목록에서 사라집니다.                             |

### FE-006 — 복구·중복 동작·마지막 페이지

**준비:** FE-005에서 삭제한 항목을 사용합니다. 중복 동작은 같은 항목을 서로 다른 두 탭에서 열어 재현합니다.

| 단계 | 수행                                                                                                                                         | 기대 결과                                                                                                                                                                         |

### 오류 재현용 수동 브라우저 절차

정상 데이터 흐름은 실제 테스트 API로 확인합니다. 아래 보조 코드는 **FE-008·009의 응답 유실·화면 오류·응답 순서 확인에만** 사용합니다. 프론트 소스나 백엔드를 바꾸지 않으며, 개발자 도구 Console에서 한 번 설치합니다. 새로고침하면 해제됩니다. 같은 페이지에서 재설치하지 않습니다.

```js
window.todoManualOriginalFetch = window.fetch.bind(window);
window.todoManualFault = null;
window.todoManualDelayAssigned = false;
window.todoManualDropNextCreate = false;
window.fetch = async (input, init) => {
  const url = new URL(
    input instanceof Request ? input.url : String(input),
    location.href,
  );
  const method = (
    init?.method ?? (input instanceof Request ? input.method : "GET")
  ).toUpperCase();
  const isTestApi = url.origin === "http://127.0.0.1:8001";
  const fault = window.todoManualFault;
  if (isTestApi && fault && url.pathname === fault.path && method === fault.method) {
    return new Response(fault.body, {
      status: fault.status,
      headers: { "Content-Type": fault.contentType ?? "application/json" },
    });
  }
  const response = await window.todoManualOriginalFetch(input, init);
  if (
    isTestApi &&
    window.todoManualDropNextCreate &&
    method === "POST" &&
    url.pathname === "/api/v1/tasks" &&
    response.ok
  ) {
    window.todoManualDropNextCreate = false;
    throw new TypeError("수동 검증: 저장 후 응답 유실");
  }
  if (
    isTestApi &&
    window.todoManualDelayAssigned &&
    method === "GET" &&
    url.pathname === "/api/v1/tasks" &&
    url.searchParams.getAll("status").includes("assigned")
  ) {
    await new Promise((resolve) => setTimeout(resolve, 3000));
  }
  return response;
};
```

예를 들어 생성 요청의 제목 오류를 표시하려면 다음 규칙을 설정한 뒤 실제 화면에서 저장을 누릅니다. 이 요청은 테스트 DB에 전달되지 않습니다. 수정 검증은 `method: "PATCH"`, `path: "/api/v1/tasks/실제숫자ID"`로 바꿉니다.

```js
window.todoManualFault = {
  method: "POST",
  path: "/api/v1/tasks",
  status: 422,
  body: JSON.stringify({
    detail: [
      { loc: ["body", "title"], msg: "제목을 확인하세요.", type: "value_error" },
    ],
  }),
};
```

규칙을 해제할 때는 `window.todoManualFault = null`로 설정합니다. 모든 수동 대체를 끝내면 `window.fetch = window.todoManualOriginalFetch`를 실행하거나 페이지를 새로고침합니다. 응답을 대체한 케이스는 결과에 `수동 모의 응답`으로 명시하며 실제 서버의 해당 오류 재현으로 기록하지 않습니다.

## 팀 칸반 수동 테스트

### 준비와 한 단계씩 진행하는 방법

1. [README](../README.md)의 칸반 환경 설정으로 백엔드와 프론트를 실행합니다. 백엔드는 Supabase `kanban-team6`의 기존 팀 보드와 작성자 설정을 사용하고, 프론트는 같은 출처의 Next.js 프록시로 호출합니다. 기존 Todo용 빈 SQLite 서버를 칸반 검증에 사용하지 않습니다.
2. `http://localhost:3000/kanban`을 브라우저 A에서 열고 개발자 도구 Network 기록을 켭니다. 실제 사용 포트가 다르면 주소를 기록합니다. 토큰과 DB 연결 문자열은 화면·캡처·기록에 복사하지 않습니다.
3. 사용할 실제 팀 업무를 하나 정합니다. 예: `과제8 발표 데모 리허설`. 실제 할 일인 경우에만 이 예시를 사용합니다. 담당자 입력은 팀에 등록된 GitHub 사용자명으로 준비하며, 등록 후 업무 ID·번호를 기록해 같은 업무를 재사용합니다.
4. 브라우저 B는 다른 브라우저 또는 별도 프로필로 엽니다. 팀원 PC를 사용하는 경우 그 PC의 프론트도 **같은 공유 보드**에 연결되어야 합니다. 다른 사람 PC에서 `localhost`는 그 사람 PC를 뜻하므로 A의 주소를 그대로 공유하지 않습니다.
5. 안내자는 **FE-KB-001의 1단계부터 한 번에 한 행만** 안내합니다. 사용자의 `통과 / 실패 / 이상한 점` 답을 받은 뒤 실제 결과를 기록하고 다음 행으로 진행합니다. 실패하면 ID·단계·예상값·실제값을 남기고 관련 케이스를 통과 처리하지 않습니다.
6. 실제 팀 보드에는 업무에 필요한 카드만 생성합니다. 오류·다중 페이지 확인용 대량 샘플은 격리 환경 또는 수동 모의 응답을 사용합니다. 현재 칸반 내용 편집·삭제는 지원하지 않으므로 기존 팀 카드를 테스트 목적으로 바꾸거나 삭제하지 않습니다.

| 4    | 완료 → 할 일 → 완료 → 진행 중 → 할 일 순으로 버튼 이동합니다. | 각 상태에서 나머지 두 상태로 이동할 수 있으며 요청·응답·화면이 일치합니다. 테스트 뒤에는 실제 업무의 현재 상태로 맞춥니다. |

### FE-KB-005 — 드래그 앤 드롭

**준비:** 데스크톱 브라우저, 실제 업무 카드 한 개. 다른 팀원이 동시에 같은 카드를 편집하지 않는 시점에 진행합니다.

| 단계 | 수행                                                                             | 기대 결과                                                                                       |
| ---- | -------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| 1    | 카드를 다른 상태 컬럼으로 끌어 놓습니다.                                         | 대상 상태로 PATCH를 보내고 성공 후 해당 컬럼에 표시합니다. 업무가 복제되거나 사라지지 않습니다. |
| 2    | A와 B를 새로고침합니다.                                                          | 드래그로 바꾼 상태가 실제 저장되어 두 브라우저에 동일하게 표시됩니다.                           |
| 3    | 카드를 현재 컬럼 안에 놓습니다.                                                  | 상태 PATCH가 추가로 발생하지 않습니다. 컬럼 안의 수동 순서 저장 기능으로 안내하지 않습니다.     |
| 4    | 업무와 관계없는 텍스트를 컬럼에 끌어 놓고, 카드 드래그를 컬럼 밖에서 취소합니다. | 잘못된 업무 요청이나 상태 이동 없이 보드가 유지됩니다.                                          |

### FE-KB-006 — 실패 복구와 중복 요청 방지

**오류 재현:** 브라우저의 Network 요청 차단으로 `/api/kanban/tasks/*`를 막거나 아래 보조 코드로 해당 브라우저의 PATCH만 실패시킵니다. 모의 오류는 실제 서버 오류와 구분해 기록합니다. 보조 코드는 서버로 PATCH를 전달하지 않으므로 공유 데이터는 변경되지 않습니다. 설치 후 페이지를 새로고침하면 해제됩니다.

```js
window.kanbanManualOriginalFetch = window.fetch.bind(window);
window.fetch = async (input, init) => {
  const url = new URL(
    input instanceof Request ? input.url : String(input),
    location.href,
  );
  const method = (
    init?.method ?? (input instanceof Request ? input.method : "GET")
  ).toUpperCase();
  if (
    url.origin === location.origin &&
    url.pathname.startsWith("/api/kanban/tasks/") &&
    method === "PATCH"
  ) {
    return new Response(JSON.stringify({ detail: "수동 테스트: 상태 저장 실패" }), {
      status: 503,
      headers: { "Content-Type": "application/json" },
    });
  }
  return window.kanbanManualOriginalFetch(input, init);
};
```

| 단계 | 수행                                                                                   | 기대 결과                                                                                                                                     |
| ---- | -------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| 1    | 실패 규칙을 적용한 상태에서 버튼으로 이동합니다.                                       | 오류가 표시되고 카드는 원래 컬럼에 남습니다. 성공 안내를 표시하지 않습니다.                                                                   |
| 2    | 같은 상태에서 드래그로 이동합니다.                                                     | 같은 실패 정책이 적용됩니다. 원래 카드가 사라지거나 목적 컬럼에 중복 표시되지 않습니다.                                                       |
| 3    | 실패 규칙을 해제하고 같은 이동을 다시 실행한 뒤 새로고침합니다.                        | 저장 성공 후 이동하며 실제 상태도 유지됩니다. 해제는 `window.fetch = window.kanbanManualOriginalFetch` 또는 새로고침으로 합니다.              |
| 4    | 느린 네트워크에서 상태 이동 버튼을 연속으로 누릅니다.                                  | 저장 중 중복 이동이 차단되고 결과가 일관됩니다.                                                                                               |
| 5    | 아직 등록하지 않은 실제 업무가 있으면 느린 네트워크에서 등록 버튼을 연속으로 누릅니다. | POST가 중복되지 않고 업무가 하나만 생성됩니다. 새 업무가 없으면 격리·모의 환경에서 실행하고 그 사실을 기록합니다.                             |
| 6    | 요청 차단 또는 모의 POST 오류로 등록 실패를 재현합니다.                                | 입력은 유지되고 성공 안내·새 카드가 생기지 않습니다. 자동 재시도가 없습니다. 응답 유실 가능성이 있으면 보드 조회 후 재등록 여부를 판단합니다. |
| 7    | GET을 차단한 뒤 새로고침을 누르고 차단 해제 후 재시도합니다.                           | 실패를 빈 보드로 표시하지 않으며 정상 연결 후 실제 카드 목록이 회복됩니다. 모든 오류 규칙을 해제합니다.                                       |
