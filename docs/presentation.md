## 3분 발표 대본

### 1. 과제 개요 — 20초

이번 과제는 이전에 만든 팀 공유 칸반 백엔드에 웹 화면을 연결하는 작업입니다. 실제 팀 업무를 등록하고 다른 브라우저에서도 같은 업무를 볼 수 있도록 구성했습니다. 기존 Todo 기능은 유지하면서 팀 칸반을 별도 메뉴로 추가했습니다.

### 2. 기술 스택과 두 테마 — 25초

프론트는 Next.js와 React, TypeScript를 사용하고 Astryx 컴포넌트에 두 디자인 테마를 적용했습니다. Productivity는 작업을 명확하게 보여주고, Warm은 따뜻한 색과 여유 있는 간격을 사용합니다. 설정 화면에서 전환합니다. 칸반은 FastAPI를 거쳐 기존 팀 Supabase 보드에 연결했고, API 토큰은 Next.js 서버에서만 사용합니다. 실제 프론트 서버 프록시 조회, 업무 저장 후 재조회와 상태 변경 API 응답을 확인했습니다.

### 3. 화면 소개 — 20초

기존 Todo에서는 상세 수정, 삭제와 복구를 사용할 수 있습니다. 팀 칸반은 할 일, 진행 중, 완료의 세 컬럼으로 구성했습니다. 카드의 상태는 드래그로 바꾸거나 이동 버튼으로 바꿀 수 있어서 모바일과 키보드로도 조작할 수 있습니다.

### 4. 실제 업무 데모 — 65초

아래 대본은 브라우저에서 실제 공유와 상태 이동을 확인한 뒤 사용합니다. 현재 칸반 DB 연결·권한, 서버 프록시 조회·상태 PATCH와 CLI 업무 저장 후 재조회는 확인했지만, 연결 후 브라우저 UI·두 브라우저 공유·실제 드래그·영상 촬영은 미완료입니다.

지금 팀에서 실제로 해야 하는 업무를 등록하겠습니다. 제목과 설명을 적고 담당자와 라벨을 넣습니다. 저장하면 할 일 컬럼에 나타납니다. 다른 브라우저에서 보드를 새로고침하면 같은 업무가 보입니다. 이제 버튼으로 진행 중으로 옮기고, 완료 컬럼으로 드래그하겠습니다. 다시 새로고침해도 상태가 유지됩니다. 화면에서만 바꾼 것이 아니라 공유 백엔드에 저장된 결과를 다시 조회한 것입니다.

### 5. 하네스와 검증 결과 — 30초

개발 루프는 명세와 테스트 번호를 정하고, 작은 동작을 구현한 뒤 전체 검사를 실행하는 방식입니다. 린트, 포맷, 엄격한 타입 검사, 단위·컴포넌트 테스트, 프로덕션 빌드를 커밋 전에도 확인합니다. 칸반은 등록과 상태 변경뿐 아니라 저장 실패 시 원위치 유지, 토큰 비공개, 두 브라우저 공유를 따로 확인합니다. 실제 통과 결과와 미확인 항목은 검증 기록으로 구분했습니다.

발표자는 이 부분에서 최신 검증 기록에 있는 **실제 검사 결과 한 줄과 남은 수동 항목 한 줄**을 짚습니다. 실행하지 않은 검사는 통과로 읽지 않습니다.

### 6. 배운 점 — 20초

화면에 카드가 보이는 것만으로 공유 기능이 완성되지는 않는다는 점을 배웠습니다. 저장한 값을 다른 브라우저에서 다시 읽어야 했고, 백엔드에 없는 상태 변경 API도 계약부터 맞춰야 했습니다. 자동 검사와 실제 브라우저 확인을 나눠 수행하면서 정상 동작과 실패 복구를 함께 점검했습니다.

## 현재 발표 준비 상태

2026-10-26 최신 검사는 **프론트 185개·백엔드 52개·CLI 51개** 통과입니다.
[프론트](https://team-todo-frontend-blush.vercel.app)와 [Python 3.13 백엔드](https://team-todo-backend-pied.vercel.app)는 Vercel READY이며, 프론트 All Deployments 인증 보호와 소유자 Chrome의 앱 로드를 확인했습니다. 비인증 `/kanban`·두 API의 HTTP 302 전환은 확인했지만 비인증 브라우저 전체 수동 검증을 통과 처리하지 않습니다.

백엔드 `/openapi.json`은 200, 무토큰 API는 401입니다. 사용자 SQL 실행과 새 연결의 권한 확인 후 칸반 DB 설정을 배포에 반영했으며, 인증된 백엔드와 프론트 프록시 GET 모두 200입니다. 실제 업무 #13은 CLI 요청의 시간 초과 뒤 GET 재조회로 저장을 확인했습니다. 같은 업무를 프론트 프록시 PATCH로 진행 중 → 완료 → 진행 중으로 이동했고 각 응답은 200·요청 상태와 일치했습니다. 일반 Todo는 별도 `DATABASE_URL` 미설정으로 503입니다. 연결 후 브라우저 UI·두 브라우저 공유·실제 드래그·영상은 아직 확인하지 않았습니다. 격리 PostgreSQL의 화면을 실제 Supabase 저장 증거로 소개하지 않습니다.

## 데모 준비와 진행 순서

1. 칸반 DB 연결·최소 수정 권한과 프론트 프록시 조회는 확인했습니다. 브라우저 조작 연결을 복구한 뒤 배포된 프론트에 허용된 계정으로 접근하고 `/kanban` 화면이 정상인지 확인합니다. 브라우저 A와 B가 같은 공유 보드를 읽는지 FE-KB-001·003으로 확인합니다.
2. 등록 시연에는 아직 등록하지 않은 실제 팀 업무 하나를 준비합니다. 이미 저장된 업무 #13 `과제 #8 칸반 배포 및 데모 영상 제작`을 같은 목적으로 다시 만들지 않습니다. 상태 이동 확인은 해당 업무 UUID를 재사용할 수 있습니다. 담당자는 팀에 등록된 GitHub 사용자명을 사용합니다.
3. 설정 화면을 한 번 열어 Productivity와 Warm을 보여준 뒤 칸반으로 돌아옵니다. 발표에서는 테마 두 개의 차이만 짧게 설명합니다.
4. A에서 업무를 등록하고 B에서 새로고침해 같은 UUID·업무 번호를 확인합니다. 화면과 녹화에 토큰·환경 변수·DB 연결 문자열을 띄우지 않습니다.
5. 버튼으로 진행 중으로, 드래그로 완료로 이동한 뒤 B를 새로고침합니다. 상태를 바꾸는 시연임을 설명하고 종료 후 실제 업무 상태로 되돌립니다.
6. 최신 [검증 기록](VERIFICATION.md)의 자동 검사 결과와 [수동 결과](TEST_CASE.md)의 실제 공유 확인을 보여줍니다. 전체 수동 조합이 미완료라면 해당 범위를 그대로 밝힙니다.
7. 실제 공유 검증이 끝나면 데모 영상을 촬영하고 녹화 일시·버전을 기록합니다. 현재 영상은 미촬영입니다. 촬영 후 라이브 연결 문제가 생길 때만 해당 녹화로 대신하며 현재 라이브 실행과 구분합니다.

## 발표에서 구분할 범위

- 과제 #8의 핵심은 과제 #7 백엔드와 실제 팀 업무 저장·공유입니다. 이 팀은 기존 저장소가 Supabase여서 그 연결을 사용합니다.
- 팀 칸반의 현재 범위는 생성·전체 조회·상태 이동입니다. 내용 편집·삭제는 미지원이며 [백엔드 API 변경 문서](KANBAN_API_CHANGES.md)에 필요한 후속 사항을 정리합니다.
- 다른 사용자의 변경은 새로고침으로 확인합니다. 실시간 동기화로 소개하지 않습니다.
- 위 검증 수치는 2026-10-26 기준입니다. 발표 직전에 최종 코드의 실제 실행 기록으로 갱신하고 미확인 수동 항목을 통과로 소개하지 않습니다.
